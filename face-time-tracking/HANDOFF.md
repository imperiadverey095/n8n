# HANDOFF — контекст, решения и следующие шаги

Файл для передачи работы между сессиями (людям и ИИ-агентам). Дополняйте раздел «Журнал» при каждой значимой итерации.

## Задача

Реализовать «Time Management AI»: учёт прихода/ухода сотрудников по распознаванию лиц с фотографий, безопасное хранение отметок в БД по профилю сотрудника, детальные отчёты и табели (тип отчёта по умолчанию — `standard`), интеграция с HR-системами, настраиваемая отчётность для HR, соблюдение законодательства о персональных данных, возможность сотрудника проверять и исправлять свои записи.

Переменные из постановки: изображение для распознавания (`image` / `image_base64`), уникальный идентификатор сотрудника (`employee_id`), тип табеля (`type=standard|detailed|summary`).

## Что сделано (итог сессии 1, 2026-09-21)

* Самотест `db/900_selftest.sql` (7 групп, ASSERT) прогнан на реальном PostgreSQL 16 — **проходит**. Демо-данные `db/002_seed_demo.sql` проверены на чистой БД.
* 8 воркфлоу n8n собраны генератором (`scripts/lib/builder.mjs` + `scripts/workflows/*.mjs`) → `workflows/*.json`. Валидатор `scripts/validate-workflows.mjs` сверил типы/версии всех нод с исходниками репозитория (437 нод) — **ок**. Конфигурации 19 ключевых нод дополнительно проверены на живом инстансе n8n пользователя через MCP `validate_node_config` — **valid**.
* Документация: README, docs/api.md, docs/reports.md, docs/hr-integration.md, docs/privacy-compliance.md, docs/n8n-node-versions.md; стенд docker-compose; скрипты импорта и smoke-теста.
* Демонстрация «один рабочий день» (`examples/`): сценарий на реальной БД, отчёты кодом воркфлоу, скриншот HTML, смоделированный HTTP-обмен терминала с воркфлоу 02; описание — `docs/walkthrough.md`.

## Ключевые решения и почему

| Решение | Почему |
|---|---|
| **CompreFace (self-hosted) как провайдер распознавания** | биометрия не покидает периметр; открытая лицензия; REST API с subject = `employee_id`; `SAVE_IMAGES_TO_DB=false` — хранятся только эмбеддинги. Альтернативы (AWS Rekognition, Azure Face) заменяются в трёх HTTP-нодах. |
| **Вся логика в SQL-функциях `fn_*`** | атомарность (FOR UPDATE на сотруднике), единые правила для всех входов (лицо/ручная/корректировка), тестируемость без n8n, воркфлоу остаются короткими. |
| **Фото передаётся как binary (multipart), не base64 в JSON** | снимок не оседает в данных выполнений n8n; в БД только sha256-хэш (нода Crypto) и схожесть. |
| **Токены API в БД с sha256, роли device/employee/hr/system** | один механизм аутентификации на все вебхуки без Enterprise-функций n8n; сотрудник видит только себя по токену, а не по параметру запроса. |
| **Идемпотентность + антидребезг + `maxSessionHours` в `fn_clock`** | терминалы шлют дубли и офлайн-очереди; чередование приход/уход не должно «закрывать» смену через сутки. |
| **Обязательное согласие + небиометрическая альтернатива (ручная отметка)** | требования GDPR ст. 9 / 152-ФЗ ст. 11; в РФ 572-ФЗ может запретить коммерческую биометрию вне ЕБС/КБС — система должна работать и без распознавания. |
| **Корректировки не удаляют историю** | старое событие помечается `corrected`/`voided` со ссылкой `superseded_by`; подотчётность. |
| **Outbox-паттерн для HR-интеграции** | доставка «хотя бы один раз», повтор с экспоненциальной паузой, независимость от конкретной HR-системы. |
| **Генератор JSON вместо ручного JSON** | 146 нод; детерминированные id (sha1 от имени) → чистые диффы; версии нод в одном месте. |
| **Версии нод «не самые новые»** (Postgres 2.5, If 2.2, HTTP 4.2, Webhook 2) | совместимость и с форком, и с облаком; Postgres ≥ 2.5 нужен ради массива в Query Parameters (JSON-аргументы). |

## Что НЕ сделано / ограничения

* Воркфлоу не запускались end-to-end с реальным CompreFace (в песочнице нет фото и инстанса) — проверены статически и валидатором инстанса. Первый прогон `scripts/smoke-test.sh` на стенде — **первый следующий шаг**.
* Нет liveness-детекции (защиты от фото на телефоне): CompreFace её не даёт. Рекомендация — SDK терминала с liveness, оценка передаётся в `liveness_score`.
* UI есть (`ui/`): терминал проходной, личный кабинет сотрудника, панель HR — страницы без сборки поверх тех же вебхуков. Чего в них нет: детекции живости, авто-съёмки без нажатия, мобильного приложения.
* Расчёт табеля покрывает типовые правила (обед, опоздания, сверхурочные, смены через полночь, производственный календарь, отпуска/больничные/командировки). Не реализованы: ночные надбавки, округление до интервалов, остатки дней отпуска (баланс), графики «сутки через трое» и суммированный учёт рабочего времени — место для них `fn_daily_summary` и `work_schedule`.
* Юридическая часть (DPIA, тексты согласий, применимость 572-ФЗ) требует юриста.

## Как продолжать работу

* Логика → `db/001_schema.sql` + сценарий в `db/900_selftest.sql` → `scripts/test-db.sh`.
* Воркфлоу → `scripts/workflows/*.mjs` → `node scripts/build-workflows.mjs && node scripts/validate-workflows.mjs` → коммит JSON вместе с исходниками.
* Версии нод и имена credentials — `scripts/lib/builder.mjs`.

### 2026-09-26 — сессия 4: развёртывание и сквозной прогон на живом n8n
* Поднят стенд без Docker: n8n 2.40.7 на Node 24, настоящая PostgreSQL 16, заглушки CompreFace (сопоставление по sha256 снимка), приёмника кадровой системы и SMTP. Прогнаны все 10 шагов сценария: регистрация, отметка по лицу, повтор с тем же `request_id`, незнакомое лицо, неверный токен, отчёты JSON и CSV, свои записи, запрос корректировки, очередь HR, одобрение с письмами.
* **Четыре дефекта, которые видно только на живой системе:**
  1. **Повторный импорт не обновлял воркфлоу.** `n8n import:workflow` делает upsert по полю `id`, а сборщик его не выставлял — каждый импорт создавал рядом второй экземпляр, вебхуки оставались за первым, и правки не доезжали до работающей системы. Диагноз занял больше всего времени: ответы webhook приходили корректные, но от старого кода. Исправлено: `idFrom()` в сборщике даёт постоянный идентификатор из имени воркфлоу. Проверено — два импорта подряд оставляют ровно 8 воркфлоу.
  2. **В аудите терялся исполнитель регистрации биометрии.** Нода Postgres отдаёт дальше только колонки своего запроса, поэтому `actor` из шага валидации исчезал, и `biometrics.enrolled` писалось с пустым исполнителем — то есть по журналу нельзя было сказать, кто зарегистрировал чужую биометрию. Узел `Attach Image` теперь восстанавливает поля из шага валидации, а не только binary.
  3. **Теги в экспорте ломали импорт каталога.** `--separate` создаёт тег на каждый файл и падает на уникальности имени; теги убраны из экспорта в `meta`.
  4. **Одно событие — два разных времени в письмах.** Кадровику время печаталось в UTC (`$now.zoneName` на инстансе отдаёт UTC), сотруднику — в его поясе. Пояс уведомлений вынесен в ноду Config и печатается рядом со временем; тип отметки переведён на русский, формат — `ДД.ММ.ГГГГ ЧЧ:ММ` вместо ISO.
* Проверено дополнительно: выгрузка в кадровую систему по расписанию дочищает очередь до нуля — за несколько тиков все 7 накопленных событий ушли со статусом `sent`, приёмник получил ровно 7 (4 `attendance.created` и 3 `employee.upserted`), повторов и потерь нет; письма доходят и содержат переведённые формулировки; незнакомое лицо даёт 404 `unknown_face`, неверный токен — 401.
* Выводы: (1) идемпотентность развёртывания — такое же требование, как идемпотентность отметки, и проверяется она только повторным запуском; (2) ноды, которые «просто отдают данные дальше», молча режут поля — всё, что нужно ниже по цепочке, надо брать явно по имени узла; (3) заглушка с состоянием в памяти переживает перезапуск теста и подсовывает результат прошлого прогона — сбрасывать её надо вместе с базой.
